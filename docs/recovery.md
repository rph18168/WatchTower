# 初始基线与近期恢复

首次真正执行自动巡检时，先持久保存该次巡检的基线截止时间，再回看最近 48 小时。历史候选形成相关摘要和已知动态；即使已核实为重大动态，也不建立历史通知，不伪造已发送记录。只处理命令、手动暂停和查询回复不会提前建立新闻基线。

基线的构建进度独立于最近成功周期时间。预算暂停、来源暂时失败和 runner 中断后继续使用原截止时间；未完成的历史候选改写标题也不会变成新通知。所有仍可处理的基线工作完成，或已经退出恢复窗口后，基线才标为完成。已经保存的摘要、动态修订、去重和发送确认继续有效。

## 有界处理

每个周期只提交一批完整候选。批次同时受输入字节和输出规模约束；OpenRouter 适配器把实际结构化 schema、指令、序列化封装及少量 SDK 余量计入选批。默认 4096 输出 token 时每批最多 5 项；较小输出上限至少尝试一项，真实请求仍由同一个预算执行器检查。输入、来源证据不会为了塞入请求而静默截断。

单个候选无法容纳时先跳过，继续选择可容纳的小项。其原始内容仍在 SQLite 中；后续可调高用量上限，或在退出 48 小时窗口后保留为历史候选。摘要、核实、动态身份比较及 SDK 的实际请求都继续共用原有费用、步数和服务方额度准入。

## 故障与预算恢复

每次巡检处理最近 48 小时内仍未完成的内容。更早的未处理候选改为 `archived`，保留原始材料和空的处理确认，不为其补造摘要。已有摘要不因归档而删除；已经完成摘要但未核实或归并的旧版本保留原记录，并退出自动处理。

来源 `network` 或 `timeout` 与完成的证据不足判断不同。近期工作最多读取三次来源，第一次失败后至少等待 15 分钟，第二次失败后至少等待 30 分钟；成功读取后复用证据补核实，不重新生成摘要。持续失败达到上限时只保留带局限的摘要，不通知。其他不可用、不完整或不支持的来源直接保留局限。模型请求失败的实际或未知费用仍由用量控制记录，来源重试不能清除未知费用或绕过月预算。

## 通知恢复

新闻通知保留产生该条修订的时间。新的实质修订使用其新候选的时间；已知帖子的内容修订使用观察到变化的时间。纯重复帖子、分数增长和额外来源不刷新旧通知的时间。

形成夜间汇总前、重试前以及每次持久化发送检查点后，都按实际时钟检查 48 小时窗口。过期新闻改为 `expired`，保留尝试记录，`sentAt` 仍为空。已确认发送的消息不受过期清理影响。恢复发送仍同时遵守上海 08:00–23:00、手动暂停和退避。

汇总持久保存成员片段。部分成员过期时保留旧汇总及尝试历史，只为仍新鲜的未确认片段建立替代汇总；已确认批次不重发，成员也不会脱离汇总逐条重复发送。替代汇总沿用原批次的限流、永久故障和退避准入，不复制成虚假的发送尝试。命令回复与当前运行报告不适用新闻候选的 48 小时规则。

## 发现边界

HN 获取仍依赖 Algolia 已索引的 `story`、至少 20 分门槛、当前 48 小时窗口和服务端可用分页。每轮固定上界，读取所有可用页面并按帖子 ID 合并重叠结果；服务端结果数超出可用分页时明确失败。索引延迟、帖子达到门槛的时间和窗口外内容都可能造成遗漏；这不是 HN 全量或行业信息全覆盖承诺。停机很久也不会无限回溯历史新闻。

这些行为已通过离线完整周期、真实 SQLite 重开和真实 SDK 协议替身验证；真实 HN、付费模型、远端状态与 Telegram 的部署验收仍属于 T10。

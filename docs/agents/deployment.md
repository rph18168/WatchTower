# 部署验收与外部等待

执行真实部署前先读[验收运行手册](../live-acceptance.md)；查询命令、报告字段和退出码见[只读验收工具](../acceptance-tools.md)。当前配置、默认分支、开关和最近运行均从实际来源读取。历史成功只证明当时的结果，历史记录见[验收档案](../acceptance/2026-11-01-spec-1.md)。

## 一次诊断的完成条件

1. 固定检查时间、仓库、默认分支、workflow ID／文件及启用时间；核实 workflow active、cron 位于默认分支、仓库未禁用／归档、两个真实运行变量，以及可见的 Actions 策略、触发 actor 和队列。未读取或无权读取的项目列为未知。
2. 用 `schedule` 命令查询启用后的真实事件。退出码 2 表示查询失败，不能写成“没有事件”；网络 EOF、无效 JSON 和不完整分页都属于查询失败。按新的诊断线索至多补做一次复核，仍失败就保存查询失败检查点。
3. 有事件时用 `run` 核实相应 attempt 的实际步骤和 checkout，再用 `snapshot`／`compare` 检查固定快照、状态延续、费用与公开边界。绿色总状态或 skipped 步骤不能替代执行证据；未知费用或真实失败立即转为有界故障诊断，预算保护保持有效。
4. 没有事件时用 `platform` 获取官方汇总及事故列表，并核对 HTTP Date／Age 和请求时间。缓存过旧或请求失败列为未知；公开状态正常不能排除未公开或单个 workflow 的调度问题。必要的手动离线对照只验证 runner／手动入口，不能证明自然定时正常。

## 退出外部等待

完成上述一轮可执行检查后，若没有新的可验证假设、只剩 GitHub 创建自然事件等外部条件，结束主动诊断，保存检查点。连续轮询、睡眠、重复叙述同一状态都不增加验收证据。新的配置故障、事件、官方事故或费用回执出现时再恢复相应分支。

检查点保存在忽略的证据目录，包含：

- 检查 UTC 时间、目标仓库／workflow、启用时间及实际代码／状态 SHA。
- 各查询成功与否、报告路径、已证实事实、未读取项目和未确定原因。
- 尚未满足的验收条件，以及下一次检查的明确时间或触发条件。

已有用户授权的后续检查，就沿用其次数、时间和通知要求；原样等待时仅保存带时间证据，状态变化、完成、故障或需要用户行动时才通知。检查次数用尽后停止；尚未授权后台检查时，在下次用户继续或相关外部证据到来后重查，不自行创建自动化。

外部等待保留验收未完成状态。只有实际证据满足手册条件后才能结项。保持现有 cron、开关、预算和状态；修复须由已确认的故障支持，不用手工派发、重置基线或制造新闻代替自然事件，不代使用者联系 Support。

# Telegram 本人查阅与控制

完整周期先使用 `getUpdates` 读取操作，再决定是否自动巡检和处理模型工作。每次读取最多 100 条更新；更多更新留待后续周期。命令由下一次实际成功运行处理，约 15 分钟的调度目标不保证即时回复或准点执行。Telegram [最多保留 24 小时的未读更新，且轮询与 webhook 互斥](https://core.telegram.org/bots/api#getting-updates)；停跑过久可能丢失旧命令。本应用不会自动修改 webhook。

通过 Actions Secrets 或进程环境提供 `TELEGRAM_BOT_TOKEN`、`TELEGRAM_CHAT_ID`、`TELEGRAM_USER_ID`。chat 和 user 都是正整数形式的本人身份；仅 chat 类型为 `private` 且两项身份同时匹配的消息可以操作。适配器闭包内完成认证，仅向周期返回更新编号与四种固定操作；凭据、身份、原消息及未授权内容不会进入 SQLite、摘要、模型输入或错误日志。

| 命令 | 行为 |
| --- | --- |
| `/digest` | 查阅已经保存的摘要及来源；长内容分为不超过 Telegram 长度限制的多条消息。 |
| `/status` | 查阅手动暂停、应用月预算、服务方最近已知额度、待处理候选、待核实及待发送数量、投递故障、最近成功周期和安全故障码。 |
| `/pause` | 暂停自动采集、付费模型工作和主动发送；继续读取和回复操作。 |
| `/resume` | 解除手动暂停；修复后的永久投递故障获得新的重试机会，保留原尝试记录。模型工作仍通过应用预算与服务方限额检查。 |

命令使用表中的完整形式，可带末尾空白；不接受参数、动态配置、编辑消息或通用聊天。`/status` 中未设 key 限额不代表账户余额无限；服务方状态标明最近检查时间，实际付费请求仍须重新检查。

命令结果和回复先保存成功，再单独保存下一次请求使用的更新游标。已处理编号与回复同事务保存，游标保存失败后重新获取同一更新不会重复执行或追加回复。[Telegram 在下一次请求传入更高 offset 时确认旧更新](https://core.telegram.org/bots/api#getupdates)。回复与新闻使用同一 SQLite 待发送队列；只有经过本人认证产生的 `command-reply` 消息可在夜间或手动暂停时发送。发送确认丢失仍可能导致重试重复，沿用通知交付约定。

自动采集或模型处理失败时，已经持久的待发送消息仍通过同一时段、暂停和重试准入交付，查询回复也可送达；周期依然以故障结果结束，保留最近成功周期。任何持久化检查点失败都会禁止开始新的发送。

预算或服务方限制阻止模型工作时，通过非模型的 `budget-status` 运行报告告知本人。同一状态变化跨周期、跨重启只排一份报告，遵守主动发送的 08:00–23:00 上海时段和手动暂停。尚未确认发送的旧报告在配置恢复、UTC 月度重置或确认服务方恢复后撤销，避免恢复后发送过时告警；已有发送尝试的记录保留撤销标记与原尝试历史，不再重试。查询回复随时可用。服务方恢复检查只查询普通 key 的额度，不发出没有工作量的模型请求。

构建后可仅处理操作，无需 `OPENROUTER_API_KEY`：

```powershell
npm start -- --commands-only --github-state
```

`--commands-only` 仍需 Telegram 身份及相应存储凭据，允许网络轮询和持久保存；不采集候选、不读取来源、不调用付费模型，也不发送主动队列。与 `--allow-paid-model` 同时提供时以仅命令模式为准。正常定时周期继续使用 `--allow-paid-model --github-state`；预算耗尽属于应用状态，不应停用整个工作流，否则无法读取恢复指令。
